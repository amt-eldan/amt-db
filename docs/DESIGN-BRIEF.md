# AMT — מעקב הזמנות · בריף מערכת לעיצוב UX/UI

מסמך מפרט מלא של המערכת הקיימת, כבסיס לעיצוב מחדש (Redesign) או לבניית Design System מותאם.
המסמך כתוב כך שאפשר להזין ממנו ישירות ל-v0 / Figma / כל כלי עיצוב, בלי לקרוא קוד.

- **מוצר:** AMT — מערכת מעקב הזמנות פנימית של Atrium Micro Technologies
- **מחליף:** קובץ אקסל בשם "מעקב הזמנות.xlsx" שנוהל ידנית
- **סביבה חיה:** https://amt-db.vercel.app
- **סטאק נוכחי:** Next.js 16 (App Router, Server Actions) · React 19 · TypeScript · Neon Postgres + Drizzle · shadcn/ui + Tailwind v4 · Vercel
- **שפה וכיוון:** עברית, RTL מלא. מזהים טכניים (P/N, מק"ט, מספרי הזמנה, שטרי מטען, מטבע) מוצגים LTR בתוך טקסט RTL.

## 1. הקשר עסקי ומשתמשים

AMT היא חברת מסחר/אינטגרציה שמוכרת רכיבים וציוד ללקוחות ארגוניים, ובעיקר לקבוצות רכש של
משרד הביטחון. תהליך העבודה: מגיעה הזמנת לקוח (PDF/סרוק/מייל) → פותחים שורות מעקב → מזמינים
מספק בחו"ל (PO) → עוקבים אחרי משלוח לפי שטר מטען (BOL) → כשהפריט מגיע השורה נסגרת → בסוף
החודש מחשבים רווחיות.

### פרסונות

| פרסונה | תדירות | מה חשוב לה | ההקשר |
|---|---|---|---|
| **אלדן — מנהל התפעול** (המשתמש העיקרי, כמעט היחיד) | כל יום, כמה פעמים ביום | לראות בשנייה מה מאחר, לסמן "הגיע" בקליק, לעדכן שדה בודד בלי טפסים | דסקטופ במשרד, לפעמים מובייל בדרך |
| **מנהל/בעלים** | פעם בחודש | סיכום רווחיות, ייצוא לאקסל | דסקטופ |
| **Agent אוטומטי** (לא אנושי) | רץ ברקע | קולט הזמנות סרוקות, ממלא שטרי מטען מהמייל | דרך API — אבל התוצרים שלו חייבים להיות **מסומנים וברי-סקירה** בממשק |

### Jobs To Be Done (בסדר חשיבות)

1. "מה מאחר עכשיו ואצל איזה לקוח?" — סריקה חזותית של מצב, לא קריאת טבלה.
2. "הפריט הגיע — סמן וזוז" — פעולה בקליק אחד, עם Undo.
3. "צריך למלא PO / ספק / מחיר קנייה לשורה" — עריכה נקודתית מהירה.
4. "הגיע PDF של הזמנה חדשה" — העלאה, חילוץ אוטומטי, אישור.
5. "כמה הרווחנו החודש?" — סיכום + ייצוא.

### עקרונות מנחים לעיצוב (נגזרים מההתנהגות הקיימת)

- **צפיפות מידע לפני אווירה.** זה מחליף אקסל. משתמש שרגיל לגריד לא סובל כרטיסים אווריריים
  עם 3 שדות. הטבלה היא הגיבור.
- **צבע = מצב, ולא דקורציה.** ארבעה מצבים בלבד, עקביים בכל המערכת.
- **קיבוץ לפי לקוח** הוא המודל המנטלי, לא רשימה שטוחה.
- **כל פעולה מסוכנת מאושרת, כל פעולה מהירה ניתנת לביטול.**
- **מה שמכונה מילאה — מסומן.** אמון נבנה מכך שרואים מאיפה בא כל נתון.

## 2. ארכיטקטורת מידע

```
/login                     — שער סיסמה משותפת (ללא ניווט)
└── (app) — Shell עם Sidebar
    ├── /                  — הזמנות פתוחות   (מסך הבית, 90% מהשימוש)
    ├── /intake            — קליטת הזמנה
    └── /monthly           — סיכום חודשי
```

Shell נוכחי: Sidebar בצד ימין ברוחב 224px (`md:w-56`) עם לוגו טקסטואלי "AMT / מעקב הזמנות",
3 קישורי ניווט עם אייקונים, וכפתור "יציאה" בתחתית. במובייל ה-Sidebar הופך לפס אופקי עליון
עם גלילה אופקית.

**הזדמנות ל-Redesign:** אין Topbar, אין breadcrumbs, אין חיפוש גלובלי, אין Command Palette
(למרות ש-`cmdk` כבר מותקן), אין Dark Mode toggle (למרות ש-`next-themes` מותקן), אין דף
הגדרות, אין תצוגת Audit Log (הנתונים קיימים ב-DB ולא נחשפים בשום מקום).

## 3. מודל הנתונים (מה שהעיצוב צריך להציג)

**היחידה האטומית של המערכת היא "שורת הזמנה" (order line), לא הזמנה.** הזמנה אחת מכילה
כמה שורות (פריטים), וכל שורה מתקדמת בנפרד: יכולה להיות שורה שהגיעה ושורה שמאחרת באותה הזמנה.
כל התצוגות, הסטטוסים והפעולות הם ברמת השורה.

### `customers` — לקוחות
| שדה | סוג | הערות לעיצוב |
|---|---|---|
| `name` | טקסט, ייחודי | לרוב **מספר** של קבוצת רכש ("134", "131") ולא שם — צריך להיראות טוב גם כמספר |
| `note` | טקסט | הסבר אנושי, למשל: קבוצת רכש משהב"ט - חטיבת מודיעין. מוצג כטקסט משני ליד השם |

### `orders` — הזמנות
| שדה | סוג | הערות |
|---|---|---|
| `orderNumber` | טקסט | LTR. שני פורמטים: `0226P02556` (רגיל) / `4441537295` (משהב"ט — 10 ספרות שמתחילות ב-444) |
| `customerId` | FK | ייחודיות: (מספר הזמנה + לקוח) |
| `orderDate` | תאריך | תאריך קבלת ההזמנה — הבסיס לשיוך לחודש בסיכום |
| `sourceFormat` | enum | `standard` \| `mod` (משהב"ט) \| `manual` — מוצג כ-Badge: רגיל / משהב"ט / ידני |
| `sourceFile` | טקסט | שם קובץ ה-PDF שממנו נקלט |

### `orderLines` — שורות (הישות המרכזית)
| שדה | תווית בממשק | סוג | מי ממלא |
|---|---|---|---|
| `pn` | P/N | טקסט LTR | קליטה |
| `sku` | מק"ט (SKU) | טקסט LTR | קליטה |
| `qty` | כמות | מספר | קליטה |
| `unitPrice` | מחיר מכירה ליח' (₪) | מספר | קליטה |
| `poNumber` | הזמנת רכש (PO) | טקסט LTR | ידני, אחרי הזמנה מספק |
| `supplier` | ספק | טקסט | ידני |
| `buyPrice` | מחיר קנייה ליח' (₪) | מספר | ידני **או** המרה אוטומטית מדולרים — **חוסר בו חוסם חישוב רווח** |
| `buyPriceUsd` | מחיר קנייה ליח' ($) | מספר | agent — כפי שהוא בהזמנת הרכש, בלי המרה |
| `fxRate` / `fxRateDate` / `fxRateSource` | שער יציג, יום פרסומו, ומי קבע | מספר / תאריך / `boi` \| `manual` | תיעוד ההמרה. מוצג מתחת למחיר בשקלים |
| `shippingCost` | עלות משלוח (₪) | מספר | ידני |
| `contractDueDate` | תאריך אספקה חוזי | תאריך | קליטה — **מניע סטטוס "מאחר"** |
| `deliveryUpdate` | עדכון אספקה | טקסט חופשי | ידני — טקסט חופשי שמשפיע על סטטוס |
| `paymentMethod` | שיטת תשלום | טקסט | ידני |
| `bol` | שטר מטען (BOL) | טקסט LTR | ידני **או** agent — **מילוי שלו = "במשלוח", לא "הגיע"** |
| `carrier` | חברת הובלה | טקסט | UPS/DHL/FedEx וכו' |
| `shipmentStatus` | סטטוס משלוח | `null` \| `in_transit` \| `delivered` \| `exception` | agent, ממה שהספקית מדווחת — **זה מה שקובע ירוק** |
| `deliveredAt` | תאריך מסירה בפועל | תאריך | agent — התאריך שהספקית נוקבת בו. **קובע איזה שער יציג נלקח** |
| `bolSource` | — | `null` \| `auto` \| `manual` | מקור השטר. `auto` ⇒ סימון אייקון בממשק |
| `bolConfidence` | — | 0..1 | ודאות ה-agent. מוצג בעריכה בלבד |
| `notes` | הערות | טקסט חופשי | ידני |
| `manualStatus` | סטטוס ידני | `null` \| הגיע \| סופק חלקי \| מאחר | דריסה ידנית שגוברת על הכל |
| `isOpen` | — | boolean | `false` = ארכיון (שורה סגורה) |

### `stagedOrders` — הזמנות סרוקות שממתינות לאישור
JSON גולמי (payload) של הזמנה שחולצה מ-PDF ע"י Claude או נשלחה מ-OCR חיצוני. **לא נכנס למעקב
עד שאדם מאשר.** זה שלב "Human in the loop" ודורש UI של סקירה + עריכה + אישור/דחייה.

### `auditLog` — יומן שינויים
כל מוטציה נרשמת: entity, action, diff (from/to לכל שדה), provenance (למשל: מזהה המייל, ציטוט,
ורמת ודאות שממנה נכתב שטר מטען). **כרגע לא מוצג בשום מסך — הזדמנות עיצובית משמעותית.**

## 4. מודל הסטטוס — לב הזהות החזותית

**חמישה** מצבים. הסטטוס **מחושב**, לא נבחר (אלא אם דורסים ידנית). סדר עדיפויות — והטבלה הזאת
היא המימוש, אחרי שגרסה קודמת שלה סתרה אותו:

| # | תנאי | סטטוס | תווית |
|---|---|---|---|
| 1 | `manualStatus = הגיע` | 🟢 green | נמסר |
| 1 | `manualStatus = סופק חלקי` | 🟠 orange | סופק חלקי / תקלה |
| 1 | `manualStatus = מאחר` | 🔴 red | מאחר |
| 2 | `shipmentStatus = delivered` | 🟢 green | נמסר |
| 3 | `shipmentStatus = exception` | 🟠 orange | סופק חלקי / תקלה |
| 4 | תאריך אספקה חוזי עבר | 🔴 red | מאחר |
| 5 | שטר מטען מלא | 🔵 blue | במשלוח |
| 6 | הטקסט החופשי מכיל "סופק" ולא "לא סופק" | 🟠 orange | סופק חלקי / תקלה |
| 7 | אחרת | ⚪ neutral | במסלול |

**ירוק = הסחורה כאן, ורק הספקית יכולה לומר את זה.** שטר מטען הוא מסמך שאומר שקרטון יצא
ממחסן, ולכן הוא קונה כחול. מסירה מאושרת גוברת על איחור (שורה שנמסרה באיחור היא ירוקה + תג
**"נמסר באיחור"**), אבל שטר מטען לבדו **לא** מבטל איחור.

ייצוג נוכחי: נקודה עגולה 10px (`size-2.5`) + גוון רקע עדין לכל השורה (8–10% אטימות) + מקרא
(Legend) מעל הטבלה.

**חובות עיצוביות:**
- הסטטוס חייב להיות קריא **גם בלי צבע** (עיוורון צבעים, הדפסה) — כרגע הנקודה היא הצבע היחיד.
  צריך אייקון/צורה/תווית שנושאת את המידע.
- הגוון על השורה כולה הוא ההתנהגות שהמשתמש מכיר מאקסל — כדאי לשמר את התחושה, אבל אפשר לשדרג
  (למשל פס צד `border-inline-start` במקום מילוי מלא, שמשאיר את הטבלה נקייה).
- הצבעים כרגע Tailwind ברירת-מחדל (`green-500`, `blue-500`, `orange-400`, `red-500`) ולא
  טוקנים סמנטיים. ב-Design System הם צריכים להיות `--status-delivered / --status-in-transit /
  --status-partial / --status-late / --status-ontrack` עם וריאנטים: dot, tint, text, border.

## 5. מפרט מסכים

### 5.1 `/` — הזמנות פתוחות (המסך היומיומי)

**מטרה:** לענות בשנייה על "מה מאחר ואצל מי", ולאפשר פעולה מיידית.

**מבנה מלמעלה למטה:**
1. **כותרת** "הזמנות פתוחות" (מתחלפת ל"שורות בארכיון") + מתג "הצג ארכיון" בקצה.
2. **3 כרטיסי סטטיסטיקה** (גריד 3 עמודות, גם במובייל): שורות פתוחות · לקוחות · מאחרות.
   "מאחרות" נצבע אדום כשהערך > 0. הכרטיסים היום סטטיים — **הזדמנות:** להפוך אותם למסננים
   קליקביליים, ולהוסיף מדדים כספיים (שווי פתוח, כמה שורות ממתינות למחיר קנייה).
3. **שורת חיפוש + סינון:** חיפוש חופשי (לקוח / מס' הזמנה / P/N / ספק / שטר מטען) עם אייקון
   זכוכית מגדלת בקצה הפנימי; Select סטטוס ברוחב 176px. שניהם client-side, מיידיים.
4. **מקרא סטטוסים** — שורת טקסט זעיר עם 4 נקודות.
5. **קיבוץ לפי לקוח:** לכל לקוח כותרת (שם + הערת לקוח + "(N שורות)") ואחריה טבלה משלו.

**עמודות הטבלה (דסקטופ, RTL):** נקודת סטטוס · מס' הזמנה · P/N (עם מק"ט כשורה משנית זעירה) ·
כמות · שווי (₪, מחושב: כמות×מחיר) · הזמנת רכש · ספק · שטר מטען (Badge + אייקון רובוט אם
אוטומטי + חברת הובלה מתחת) · תאריך יעד · פעולות.

**פעולות לכל שורה (4 כפתורים בגובה 28px):**
| פעולה | סוג | התנהגות |
|---|---|---|
| ✓ **הגיע** | outline, טקסט ירוק | Optimistic — צובע מיד ירוק, Toast עם כפתור "ביטול". מוסתר אם כבר "הגיע" |
| ✎ **ערוך** | ghost | פותח Sheet מהצד |
| 🗄 **סגור / פתח** | ghost | העברה לארכיון / החזרה. Toast |
| 🗑 **מחק** | ghost, destructive | AlertDialog: "פעולה זו אינה הפיכה" |

**מובייל (`< md`):** הטבלה מוחלפת בכרטיסים. כל כרטיס: נקודת סטטוס + P/N + שווי בשורה עליונה,
ואחריה גריד 2 עמודות של פרטים זעירים (הזמנה, כמות, ספק, יעד, רכש, שטר מטען), ואחריה אותם
4 כפתורי פעולה. **חלשה:** 4 כפתורים בשורה במובייל צפופים מדי — מועמד ל-Dropdown או Swipe.

**מצבים ריקים:** "אין עדיין הזמנות במערכת. אפשר לקלוט הזמנה חדשה במסך הקליטה." /
"לא נמצאו שורות מתאימות לחיפוש או לסינון." (מובחנים — יש לשמר את ההבחנה).

**מצב טעינה:** Skeleton — כותרת, 3 קופסאות סטטיסטיקה, שורת חיפוש, גוש טבלה.

**מה חסר (למעצב):** מיון עמודות, בחירה מרובה + פעולות באצווה, ניהול Views שמורות
("רק מאחרות של לקוח 134"), פאגינציה/וירטואליזציה (כרגע כל השורות נטענות ומסוננות בדפדפן),
תצוגת Timeline/Kanban לפי מצב משלוח, קיבוץ לפי ספק או לפי חודש יעד.

### 5.2 `/intake` — קליטת הזמנה

רוחב מוגבל (`max-w-4xl`), שלושה בלוקים מלמעלה למטה — וזה גם סדר העדיפויות:

**א. העלאת PDF** — אזור Drag & Drop + כפתור בחירת קבצים, תומך מספר קבצים במקביל.
לכל קובץ שורת התקדמות עם 4 מצבים: ממתין / מחלץ / הצליח / נכשל (אייקון + טקסט; "מחלץ" עם
ספינר). החילוץ נעשה ע"י Claude בשרת ומחזיר: מספר הזמנה, לקוח, מספר שורות, ואזהרות
(Toast כתום לכל אזהרה). הקובץ **לא** נכנס למעקב — הוא נכנס ל-staging.

**ב. ממתינות לאישור** — כותרת עם Badge של מספר הפריטים, ואחריה כרטיס לכל הזמנה סרוקה:
- מסגרת ורקע ענבר (amber) שמסמנים "טיוטה, דורש תשומת לב"
- כותרת: אייקון מסמך + מספר הזמנה + לקוח + Badge פורמט (רגיל/משהב"ט/ידני) + Badge שם קובץ
- שדות כותרת ניתנים לעריכה במקום: לקוח, מספר הזמנה, תאריך הזמנה
- טבלת שורות ניתנת לעריכה במקום (P/N, מק"ט, כמות, מחיר, אספקה חוזית, מחיקת שורה)
- תחתית: תאריך הקליטה + "דחה" (destructive, מאשר במודל) + "אשר והוסף למעקב"
- אם ההזמנה כבר קיימת: AlertDialog "הזמנה כפולה — לאשר בכל זאת?"
- ריק: קופסה מקווקוות "אין הזמנות סרוקות שממתינות לאישור."

**ג. הזנה ידנית** — כרטיס "הזנה ידנית": Combobox לקוח (חיפוש + יצירת לקוח חדש), מספר הזמנה,
תאריך; ואחריהם טבלת שורות דינמית (P/N, מק"ט, כמות, מחיר ליח', תאריך אספקה חוזי, מחיקה) עם
"+ הוסף שורה" ו-"הוסף למעקב". זיהוי חכם: מספר הזמנה שמתחיל ב-444 ⇒ הודעת ענבר "הזמנת משהב"ט —
הלקוח הוא מספר קבוצת הרכש (למשל 134), לא 'משרד הביטחון'."

**הזדמנויות:** אין תצוגה של ה-PDF המקורי מול השדות שחולצו (Side-by-side review הוא הפרדיגמה
הנכונה לאישור חילוץ AI); אין סימון ברמת השדה של "מה Claude לא היה בטוח לגביו"; אין diff מול
ההזמנה הכפולה שנמצאה; שלושת הבלוקים מתחרים על אותו מסך בלי היררכיה ברורה.

### 5.3 `/monthly` — סיכום חודשי

- כותרת + הערה: "מציג שורות סגורות בלבד (לפי חודש קבלת ההזמנה)"
- Select חודש (עברית: "יולי 2026") + כפתור "ייצוא CSV" (BOM לעברית באקסל, שם קובץ עברי)
- 3 כרטיסי סיכום: סה"כ מכירות · סה"כ רווח (ירוק/אדום לפי סימן, עם תת-שורת ענבר "N שורות
  ממתינות למחיר קנייה") · מספר שורות
- טבלה: לקוח, מס' הזמנה, תאריך, P/N, ספק, כמות, מכירה ליח', קנייה ליח', סך מכירה, רווח
  (Badge "ממתין" כשחסר מחיר קנייה; אדום כשהרווח שלילי)
- מובייל: כרטיסים מצומצמים
- ריק: "אין שורות סגורות בחודש יולי 2026."

**נוסחאות:** `שווי = כמות × מחיר מכירה` · `רווח = (מכירה − קנייה) × כמות − משלוח`.
חסר מחיר קנייה ⇒ הרווח `null` ⇒ מוצג "ממתין" ו**מוחרג מהסכום** (המצב הזה נפוץ וצריך עיצוב
מכובד, לא כשגיאה).

**הזדמנויות:** אין ולו גרף אחד — למרות שכל טוקני `--chart-1..5` מוגדרים. מועמדים: מכירות ורווח
לפי חודש, שולי רווח לפי לקוח, תמהיל ספקים. אין השוואה לחודש קודם, אין מיון, אין drill-down
משורה בסיכום לשורה במעקב.

### 5.4 `/login`

כרטיס ממורכז `max-w-sm`: כותרת "AMT — מעקב הזמנות", "יש להזין את סיסמת המערכת", שדה סיסמה
(LTR, autofocus), הודעת שגיאה, כפתור "כניסה" / "מתחבר...". סיסמה משותפת אחת, בלי שם משתמש.
הקוד מוכן להחלפה ב-Auth רב-משתמשי — **כדאי לעצב מראש עבור מספר משתמשים** (אווטאר, שם, תפקידים).

### 5.5 עריכת שורה — Sheet (הרכיב המשמעותי ביותר לשיפור)

נפתח מצד שמאל (`side="left"` ב-RTL = הצד ה"רחוק"), רוחב `sm:max-w-md`, גולל.
- כותרת "עריכת שורה" + תת-כותרת: לקוח · מס' הזמנה · P/N
- **גריד 2 עמודות שטוח של 13 שדות** בלי שום קיבוץ: כמות, מחיר מכירה, PO, ספק, מחיר קנייה,
  עלות משלוח, תאריך אספקה חוזי, שיטת תשלום, שטר מטען, חברת הובלה, עדכון אספקה (textarea),
  הערות (textarea), סטטוס ידני (Select עם "אוטומטי (לפי הנתונים)" כברירת מחדל)
- אם השטר מולא אוטומטית: פסקה זעירה "שטר המטען מולא אוטומטית על ידי מעקב המשלוחים (ודאות 0.95).
  שמירה כאן מסמנת אותו כמאומת."

**בעיות לפתרון בעיצוב:** אין קיבוץ לוגי (מסחרי / רכש / משלוח / מצב), אין הדגשה של השדות
שבאמת ממולאים ביום-יום (PO, ספק, מחיר קנייה, שטר מטען), אין הצגת השפעה ("מילוי שטר מטען
יסמן את השורה כהגיעה"), אין היסטוריית שינויים (למרות שה-Audit Log קיים), אין ניווט
"שורה הבאה" בלי לסגור, אין תצוגת רווח מחושב בזמן אמת בעת הקלדת מחיר קנייה.

## 7. דרישות RTL ובינאום (קריטי — כאן נשברים עיצובים)

1. **RTL הוא ברירת המחדל**, לא מצב חלופי. `<html lang="he" dir="rtl">` + `Direction.Provider` של Radix.
2. **תוכן LTR בתוך RTL** — כל אלה חייבים `dir="ltr"` ולרוב יישור לקצה: מספרי הזמנה, P/N, מק"ט,
   PO, שטר מטען, סכומים, תאריכים. בתוך משפט עברי משתמשים ב-`<bdi dir="ltr">` כדי שהניקוד
   הדו-כיווני לא יקרוס.
3. **תכונות לוגיות בלבד** — `start/end`, `ps/pe`, `border-inline-start`. לעולם לא `left/right`.
4. **הצד ה"נכון" של Sheet/Drawer** — נפתח מ-`side="left"`, שהוא הצד המרוחק ב-RTL.
5. **אייקונים כיווניים** (חצים, chevrons) צריכים היפוך; אייקוני סטטוס לא.
6. **טקסט עברי ארוך יותר מאנגלית** ב-~15-20% — תוויות כפתורים וכותרות עמודות צריכות מרווח נשימה.
7. **ייצוא CSV** דורש BOM כדי שאקסל יפתח עברית נכון.

## 9. בריף Redesign — מה לפתור

### יעדים
1. **זהות מותג.** המערכת חסרת אישיות לחלוטין. צריך פלטה, לוגו, ואופי שמתאים לחברת
   טכנולוגיה/הגנה: מדויק, שקט, אמין. לא SaaS צעקני.
2. **הטבלה כמוצר.** הזמנות פתוחות היא 90% מהשימוש. צפיפות, מיון, פעולות באצווה, עמודות
   מותאמות, וסריקה חזותית ברמה שמתחרה באקסל.
3. **סטטוס נגיש.** להעביר את המצב במידע ולא רק בצבע.
4. **חוויית סקירת AI.** קליטת PDF וסקירת שטרי מטען אוטומטיים הן החוויות ה"חדשות" שאין להן
   מקבילה באקסל — הן צריכות עיצוב שמייצר אמון: מקור, ודאות, השוואה למקור, אישור מכוון.
5. **שקיפות (Audit).** להפוך את יומן השינויים לתצוגה — היסטוריה בשורה, "מי/מה שינה ומתי".
6. **Dark Mode אמיתי** — התשתית קיימת, צריך עיצוב ומתג.
7. **מובייל שימושי בשטח** — לא רק "לא שבור": פעולות בהישג אגודל, כרטיסים ממוקדים.

### אילוצים לא לשבור
- עברית RTL מלאה, כולל תוכן LTR משולב.
- ארבעה מצבי סטטוס בדיוק, עם אותה סמנטיקה ואותו סדר עדיפויות.
- שורה (לא הזמנה) היא היחידה שעליה פועלים.
- קיבוץ לפי לקוח במסך הראשי.
- שדות חסרים הם מצב נורמלי — `—` ו"ממתין" הם עיצוב, לא שגיאה.
- מחיקה בלתי-הפיכה חייבת אישור; פעולה מהירה חייבת Undo.
- Tailwind v4 + shadcn/ui + Radix (הטוקנים ב-`src/app/globals.css`, `oklch`).
- משתמש בודד היום, אבל להיערך לרב-משתמשים.

### מדדי הצלחה
- זמן מכניסה למסך עד זיהוי "מה מאחר": < 3 שניות.
- סימון "הגיע": קליק אחד, בלי אישור, עם ביטול.
- אישור הזמנה סרוקה מ-PDF: פחות מדקה, כולל בדיקה מול המקור.
- אפס טעויות שיוך לקוח בהזמנות משהב"ט (המקום שבו טועים היום).
