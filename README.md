# AMT — מערכת מעקב הזמנות

מערכת ניהול הזמנות פנימית של Atrium Micro Technologies, המחליפה את קובץ האקסל "מעקב הזמנות.xlsx".

- **Next.js 16** (App Router, Server Actions) + **TypeScript**
- **Neon** (Postgres serverless) + **Drizzle ORM**
- **shadcn/ui** + Tailwind, עברית RTL מלאה
- פריסה: **Vercel**

**סביבה חיה:** https://amt-db.vercel.app · ריפו: https://github.com/amt-eldan/amt-db (מחובר ל-Vercel — כל `git push` ל-`main` מפעיל deploy אוטומטי).

## מסכים

| מסך | נתיב | תיאור |

| הזמנות פתוחות | `/orders` | המסך היומיומי: קיבוץ לפי לקוח, סטטוס צבעוני, פעולות מהירות (הגיע / עריכה / סגירה / מחיקה), חיפוש וסינון |

| חשבוניות ספק | `/invoices` | רשימת החשבוניות שהתקבלו, העלאת PDF (חילוץ אוטומטי) או הזנה ידנית, וצפייה במסמך המצורף |

## התקנה מקומית

```bash
npm install
copy .env.example .env.local     # ולערוך את הערכים
npm run db:migrate               # יצירת הטבלאות ב-Neon
npm run db:seed                  # (רשות) נתוני דוגמה
npm run dev                      # http://localhost:3000
```

## פריסה ל-Vercel

```bash
npx vercel login
npx vercel --prod
```

**המיגרציות רצות לבד בכל deploy.** `npm run build` מריץ `npm run db:migrate` לפני `next build`,
כך שטבלה חדשה נוצרת ב-Neon לפני שהקוד שמשתמש בה עולה לאוויר — בלי לזכור שלב ידני. מיגרציה
שנכשלת מפילה את ה-deploy במקום להעלות עמוד שיפול על טבלה חסרה (זה מה שקרה ל-`/invoices`:
הקוד עלה, `supplier_invoices` לא נוצרה, והעמוד החזיר "בעיה בחיבור למסד הנתונים").

בלי `DATABASE_URL` הסקריפט מדלג בשקט, כך ש-build מקומי או preview בלי משתני סביבה לא נשבר.

**המיגרציות כתובות כך שאפשר להריץ אותן על מסד שהסכימה שלו כבר עודכנה בלי שהמיגרציה נרשמה**
(מה שקורה אחרי `drizzle-kit push` או שינוי ידני): כל `CREATE TABLE` הוא `IF NOT EXISTS`, כל
`ADD COLUMN` הוא `IF NOT EXISTS`, וכל `ADD CONSTRAINT` עטוף ב-`DO $$ ... EXCEPTION WHEN
duplicate_object $$` (ל-Postgres אין `ADD CONSTRAINT IF NOT EXISTS`). זה מה שמאפשר למסד להתיישר
מעצמו: כל אובייקט שכבר קיים מדולג, מה שחסר נוצר, והמיגרציות נרשמות. מיגרציה חדשה מ-`db:generate`
מגיעה בלי ההגנות האלה — אם היא נוגעת בטבלה שקיימת בפרודקשן מ-push, כדאי להוסיף אותן.

ואז מגדירים את משתני הסביבה ב-Vercel (Project → Settings → Environment Variables) ועושים redeploy. לחלופין:

```bash
npx vercel env add DATABASE_URL production
npx vercel env add APP_PASSWORD production
npx vercel env add INGEST_TOKEN production
npx vercel env add BOL_AGENT_TOKEN production
```

## API לקליטת הזמנות סרוקות (OCR חיצוני)

```
POST /api/staged
Authorization: Bearer <INGEST_TOKEN>
Content-Type: application/json
```

גוף הבקשה — הזמנה אחת או מערך של הזמנות:

```json
{
  "customer": "134",
  "customerNote": "קבוצת רכש משהב\"ט - חטיבת מודיעין",
  "orderNumber": "4441537295",
  "orderDate": "2026-07-15",
  "sourceFormat": "mod",
  "sourceFile": "4441537295.pdf",
  "warnings": ["שדה הכמות בשורה 2 מטושטש"],
  "lines": [
    {
      "pn": "CH-USB-2-1.0AB",
      "sku": "10-813580624",
      "qty": 50,
      "unitPrice": 12.5,
      "contractDueDate": "2026-08-01",
      "notes": null
    }
  ]
}
```

- `sourceFormat`: `standard` | `mod` | `manual`
- תאריכים בפורמט ISO ‏`yyyy-mm-dd`
- `warnings` (רשות) — מערך מחרוזות בעברית, כל דבר שדורש עין אנושית. מוצג בבירור בכרטיס
  האישור עד שההזמנה מאושרת או נדחית, ונשמר ב-`audit_log` בשתי הדרכים. אותו מנגנון משמש את
  חילוץ ה-PDF הידני.
- מספרים: אפשר לשלוח מספר או מחרוזת. סימני `₪`/`$` ופסיקי אלפים מנוקים (‏`"₪1,200"` → ‏1200).
- תשובה: `201 { ok: true, ids: [...] }`, שגיאת ולידציה: `422`
- ההזמנות מופיעות במסך "קליטת הזמנה" ככרטיסים לאישור/עריכה/דחייה.

**חשוב — הזמנות משהב"ט:** מספר הזמנה של 10 ספרות שמתחיל ב-444. שדה `customer` חייב להיות מספר קבוצת הרכש ('134', '131' וכו'), לא "משרד הביטחון".

## API למעקב שטרי מטען (agent חיצוני)

במקום לסרוק את תיבת המייל בעיוורון ולתחזק קובץ אקסל נפרד, **המערכת מכתיבה את החיפוש**: היא
יודעת אילו שורות פתוחות עדיין חסרות שטר מטען, ומספקת לכל אחת את מפתחות החיפוש. ה-agent מחפש
במייל לפי המפתחות האלה ומחזיר את המספר שמצא — והמערכת כותבת אותו לשורה המדויקת.

**גם הכיוון ההפוך עובד:** התקבל במייל שטר מטען חדש ויש TRACKING NUMBER, בלי שאף worklist ביקש
אותו? שולחים את המספר ואת ה-P/N שמופיע במייל, **והמערכת מאתרת בעצמה את השורה בהזמנות הפתוחות
לפי ה-P/N ומעדכנת בה את שדה שטר המטען (BOL)** — בלי `lineId` ובלי לדעת כלום על המסד. אם יותר
משורה פתוחה אחת מתאימה, לא נכתב כלום ומדווח דילוג לבדיקה ידנית.

### 1. קבלת רשימת העבודה

```
GET /api/bol/worklist
Authorization: Bearer <BOL_AGENT_TOKEN>
```

תשובה — רק שורות פתוחות שחסר בהן שטר מטען, הדחופות קודם:

```json
{
  "ok": true,
  "count": 1,
  "lines": [
    {
      "lineId": 42,
      "orderNumber": "4441537295",
      "customer": "134",
      "pn": "CH-USB-2-1.0AB",
      "sku": "10-813580624",
      "poNumber": "PO-8871",
      "supplier": "AXTON",
      "contractDueDate": "2026-08-01"
    }
  ]
}
```

### 2. החזרת שטרי מטען שנמצאו

```
POST /api/bol/matches
Authorization: Bearer <BOL_AGENT_TOKEN>
Content-Type: application/json
```

גוף הבקשה — התאמה אחת או מערך. יש **שתי דרכים** לומר לאיזו שורה המספר שייך, וצריך אחת מהן:

**א. `lineId`** — זה שהתקבל ב-worklist. קושר את המספר לשורה אחת ויחידה, בלי שהמערכת מחפשת שוב:

```json
[
  {
    "lineId": 42,
    "bol": "1Z999AA10123456784",
    "carrier": "UPS",
    "confidence": 0.95,
    "statusText": "Delivered",
    "sourceEmailId": "18fabc123",
    "sourceQuote": "Your UPS shipment for PO-8871 has been delivered"
  }
]
```

**ב. מפתחות מהמייל — `pn` / `poNumber` / `orderNumber`** — למייל שהגיע מעצמו, בלי worklist מאחוריו.
הגיע שטר מטען חדש ויש TRACKING NUMBER? מספיק לשלוח את המספר ואת ה-P/N שמופיע במייל, **והמערכת
תאתר בעצמה את השורה הפתוחה ותכתוב בה את שדה שטר המטען (BOL)**:

```json
[
  {
    "bol": "1Z999AA10123456784",
    "pn": "CH-USB-2-1.0AB",
    "poNumber": "PO-8871",
    "supplier": "AXTON",
    "carrier": "UPS",
    "sourceEmailId": "18fabc123",
    "sourceQuote": "Tracking number for P/N CH-USB-2-1.0AB: 1Z999AA10123456784"
  }
]
```

איך האיתור עובד (`resolveBolLine` ב-`src/lib/bol-match.ts`, טהור ומכוסה בטסטים):

- **כל מפתח שנשלח חייב להתאים** — מפתחות מצמצמים, לא מתחרים. "P/N X בהזמנה Y" תמיד מדויק יותר
  מ-"P/N X", ולעולם לא פחות.
- **P/N מושווה גם למספר הקטלוגי** (`sku`) של השורה, ובהשוואה מנורמלת: מקפים, רווחים ורישיות הם
  רעש, ולכן `ch usb 2 1.0ab` ו-`CH-USB-2-1.0AB` הם אותו פריט.
- **שורות שכבר יש בהן שטר מטען מוסרות מהמועמדות** — כך שמייל שני על אותו P/N הולך לשורה שעוד
  מחכה למספר, ולא מתנגש בזו שמולאה.
- **`supplier` הוא אישוש בלבד** ומשמש רק כשובר-שוויון (שם השולח כמעט לעולם לא מאוית כמו שלנו).
  לבד הוא לא מזהה שורה, ובקשה בלי `lineId` ובלי `pn`/`poNumber`/`orderNumber` נדחית ב-422.
- **מספר שורות שמתאימות → לא נכתב כלום.** אותו P/N חוזר בין הזמנות, ואיתור עמום הוא לא החלטה
  שריצה לא-מפוקחת מקבלת. מוחזר `2 open lines match pn=… (lines 4, 7) — needs manual review`,
  ואלדן מזין את המספר ידנית.

תשובה מפרטת מה נכתב ומה לא (כולל לפי איזה מפתח נמצאה השורה), כדי שה-agent ידווח על הדילוגים
בסיכום היומי:

```json
{
  "ok": true,
  "written": 1,
  "skipped": 1,
  "results": [
    { "lineId": 42, "status": "written", "matchedBy": "pn" },
    { "lineId": null, "status": "skipped", "reason": "no line matches pn=XYZ-1" }
  ]
}
```

### סדר עדיפות המפתחות בחיפוש

1. **`poNumber`** — הזמנת הרכש שלנו לספק; מופיע באישורי המשלוח שלו. האות החזק ביותר.
2. **`pn`** — מפריד בין פריטים במשלוח שמכסה כמה שורות. חוזר על עצמו בין הזמנות, ולכן כשהוא לבד
   ומתאים לכמה שורות פתוחות — ההתאמה מדולגת לבדיקה ידנית ולא נכתבת בניחוש.
3. **`orderNumber`** — משני; הספק לרוב לא מכיר אותו. שימושי בעיקר כשובר-שוויון ל-`pn`.
4. **`supplier`** — אישוש בלבד (דומיין/שם השולח).

מייל אחד שמכסה כמה פריטים → כמה התאמות, אחת לכל פריט (`lineId` או `pn` נפרד), עם אותו
`sourceEmailId`.

### מה המערכת לא תיתן ל-agent לעשות

הכתיבה לא מפוקחת ולא הפיכה מצד ה-agent, ולכן היא מוגנת:

- **שורה אחת או כלום** — התאמה עמומה לפי P/N מדווחת, לא מנוחשת (ראה למעלה).
- **לא דורסת** שטר מטען קיים — לא של אלדן ולא של ריצה קודמת. במקרה של ערך שונה מוחזר
  `bol already set to a different value — needs manual review`.
- **רק שורות פתוחות.**
- **התאמה עמומה לא נכתבת בניחוש** — `confidence` מתחת ל-0.5 מדולג ומדווח. התאמה בלי
  `confidence` נחשבת מאושרת ע"י ה-agent.
- **כל כתיבה מתועדת** ב-`audit_log` עם מזהה המייל, הציטוט, רמת הוודאות ולפי איזה מפתח נמצאה
  השורה (`matchedBy` + המפתחות שנשלחו) — אפשר לראות בדיוק מאיפה כל מספר בא ולמה הוא נחת שם.
- שורות שמולאו אוטומטית מסומנות בממשק (אייקון + הודעה במסך העריכה). עריכה ידנית של שטר
  המטען מעבירה אליו בעלות (`bol_source` הופך ל-`manual`).

ריצה חוזרת בטוחה: worklist כבר לא מחזיר שורות שמולאו, ולכן אין כפילויות.

## Connector ל-claude.ai (MCP) — אותו מעקב, ממשימה מתוזמנת

ה-REST API שלמעלה עובד מכל מקום שאפשר לשלוח ממנו בקשה עם טוקן. **משימה מתוזמנת ב-claude.ai
היא לא מקום כזה:** הסנדבוקס שלה חסום ליציאה לאינטרנט ואין בו secret store, כך שאי אפשר לא
לפתוח את הדומיין ולא להחזיק בו טוקן. Custom connector נקרא מהתשתית של Anthropic ולא מתוך
הסנדבוקס, וזה עוקף את שני החסמים — אבל הוא מדבר MCP בלבד. לכן יש כאן endpoint שני, שמדבר
MCP ומפעיל **בדיוק את אותו קוד** (`src/lib/bol-write.ts`): שני מסלולים שכותבים ל-`bol`
בשתי לוגיקות נפרדות זה בדיוק הבאג שההגנות למעלה נועדו למנוע.

**הכתובת:**

```
https://amt-db.vercel.app/api/mcp/<BOL_AGENT_TOKEN>
```

הטוקן בכתובת ולא בכותרת, כי קונקטור ב-claude.ai שומר כתובת אחת ובלי headers. לכן:

- **הכתובת היא הסוד.** להתייחס אליה כמו לסיסמה — לא לשתף, לא להדביק בצ'אט, לא בצילום מסך.
- טוקן שגוי, או `BOL_AGENT_TOKEN` שלא מוגדר בסביבה, מקבלים **404** ולא 401 — מי שמנחש לא
  מקבל אישור שהנתיב קיים בכלל.
- ההשוואה timing-safe (`crypto.timingSafeEqual` על SHA-256 של שני הצדדים), כדי שלא יהיה
  אפשר לחלץ את הטוקן תו-אחר-תו לפי זמן התשובה.
- החלפת טוקן = החלפת `BOL_AGENT_TOKEN` ב-Vercel והדבקת הכתובת החדשה בקונקטור. זה מבטל גם
  את הגישה ל-REST API באותו רגע.

### הכלים

| כלי | מה הוא עושה |
|---|---|
| `bol_worklist` | בלי פרמטרים. מחזיר את אותן שורות בדיוק כמו `GET /api/bol/worklist`, כולל מפתחות החיפוש ו-`buyPriceUsd` שכבר ידוע. סדר העדיפות (`poNumber` ← `pn` ← `orderNumber` ← `supplier`) כתוב ב-description של הכלי, כך שהסוכן מקבל אותו בלי שצריך לחזור עליו בהנחיה. |
| `bol_submit_matches` | מקבל `matches` — התאמה אחת או מערך, באותה סכימה של `POST /api/bol/matches` (ה-JSON Schema שהסוכן רואה נוצר מ-`bolMatchInput` עצמה, ולכן לא יכול להיפרד ממנה). מחזיר את אותו `{ ok, written, skipped, results }`. |
| `shipment_worklist` | **חדש.** ההיפך מ-`bol_worklist`: השורות שיש להן שטר מטען והמשלוח שלהן עוד לא נמסר — אלה שצריך לבדוק איפה הם. הישנות ראשונות (`shipment_status_at nulls first`), כך שריצה חלקית מבזבזת את עצמה על מה שהכי מיושן. `?limit=` אופציונלי (1..500, ברירת מחדל 200). מקביל ל-`GET /api/bol/shipments`. |
| `shipment_update` | **חדש.** מקבל `updates` — עדכון אחד או מערך. `lineId` חובה (לעדכון סטטוס אין לפי מה לחפש). `status` / `statusText` / `deliveredAt` / `etaDate` / `buyPriceUsd` / `carrier`. מקביל ל-`POST /api/bol/status`. מחזיר `{ ok, written, unchanged, skipped, results }`, וכל תוצאה שנכתבה מפרטת אילו שדות באמת זזו. |

**למה שני מסלולי כתיבה ולא אחד.** `bol_submit_matches` עונה על "מצאתי מספר לשורה שלא היה
לה", וההבטחה המרכזית שלו היא ש**הוא לא דורס `bol` לעולם**. `shipment_update` עונה על "המשלוח
הזה הגיע לכאן", רץ פעמיים ביום על אותה שורה כל עוד המשלוח באוויר, ו**אמור** להחליף את התשובה
הקודמת. פונקציה אחת שעושה את שניהם הייתה חייבת לוותר על כלל אי-הדריסה שמגן על `bol`.

ההגנות של `shipment_update`:

- **לא נוגע ב-`bol`** בכלל. דיווח סטטוס לא מייצר, מתקן או מוחק מספר מעקב.
- **לא כותב כששום דבר לא השתנה** — אחרת משלוח ששוהה שלושה שבועות באוויר היה משאיר ארבעים
  שורות זהות ב-`audit_log` וקובר את המעברים האמיתיים.
- **לא דורס `delivery_update`** שאדם כתב, ולא **`buy_price`** שאדם הזין.
- **מסרב לשורה בלי שטר מטען** — מפנה ל-`bol_submit_matches`.
- `deliveredAt` הוא התאריך ש**הספקית** נוקבת בו, לא היום שבו קראנו. הוא מה שקובע איזה שער
  יציג נלקח, ולכן תאריך שגוי הוא רווח שגוי.

כל ההגנות שבפרק הקודם חלות כאן — אותה פונקציה כותבת: לא דורס שטר מטען קיים, רק שורות
פתוחות, מדלג על `confidence` מתחת ל-0.5, לא דורס הערה אנושית ב-`delivery_update`, וכל כתיבה
נרשמת ב-`audit_log` עם מזהה המייל והציטוט.

stream לפתוח ואין session לשחזר).

### "Couldn't register with the sign-in service" — מה זה אומר

לפני שקונקטור מדבר MCP הוא מחפש שירות התחברות, בכתובות כמו
`/.well-known/oauth-protected-resource` (וגם עם נתיב המשאב בסוף:
`/.well-known/oauth-protected-resource/api/mcp/<token>`). לשרת הזה **אין** OAuth — הטוקן
הוא בכתובת — ולכן התשובה הנכונה לחיפוש היא 404 נקי, וה-proxy מחזיר בדיוק את זה.

זה לא היה מובן מאליו: ברירת המחדל של האפליקציה היא להפנות כל נתיב לא מוכר ל-`/login`, כך
שהחיפוש היה מקבל 307 ואז **200 עם דף HTML** במקום שבו הוא מצפה למטא-דאטה של OAuth. קונקטור
שרואה את זה חושב שיש שירות התחברות, מנסה להירשם אליו ונכשל — וזאת בדיוק ההודעה
"Couldn't register with … sign-in service". אם היא חוזרת, אלה שתי הבדיקות:

```bash
# 1. הקוד בכלל באוויר? (404 כאן = הענף לא מוזג / לא נפרס)
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://amt-db.vercel.app/api/mcp/$BOL_AGENT_TOKEN \
  -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

# 2. חיפוש ההתחברות מחזיר 404 ולא דף התחברות? (חייב להיות 404)
curl -s -o /dev/null -w '%{http_code}\n' -L \
  https://amt-db.vercel.app/.well-known/oauth-protected-resource
```

### חיבור ב-claude.ai

1. **Settings → Connectors → Add custom connector**, ולהדביק את הכתובת המלאה עם הטוקן.
   אין מה למלא ב-OAuth — האימות הוא הכתובת עצמה.
2. לפתוח את המשימה המתוזמנת ולסמן בה **שלושה** דברים: הקונקטור הזה (לשם כותבים), **Gmail**
   (משם קוראים שטרי מטען חדשים), ו**גלישה/חיפוש באינטרנט** (כדי להיכנס לאתרי המעקב של
   FedEx / DHL / UPS ולקרוא את הסטטוס האמיתי).

### התזמון: פעמיים ביום

**10:00 ו-15:00** שעון ישראל. אין cron בשרת ואין `vercel.json` — התזמון יושב במשימה
המתוזמנת ב-claude.ai, ולכן זה גם המקום לשנות אותו. שתי הרצות ביום = שתי משימות מתוזמנות
(או משימה אחת עם שני זמנים, לפי מה שהממשק מאפשר באותו רגע).

**הריצה idempotent.** אפשר להריץ אותה ידנית מתי שרוצים, וגם פעמיים ברצף: `shipment_update`
לא כותב כלום כששום דבר לא השתנה, ולכן ריצה חוזרת לא מייצרת שורות `audit_log` מיותרות ולא
דורסת כלום.

### סדר העבודה שהמשימה מקבלת

הנוסח המלא יושב ב-`instructions` של ה-MCP (`src/lib/mcp.ts`) — המשימה מקבלת אותו אוטומטית
בהתחברות, ולכן אין צורך לחזור עליו בפרומפט. בקצרה:

**א. איפה נמצאים המשלוחים שכבר יש להם שטר מטען**
1. `shipment_worklist` → כל שורה עם `bol`, `carrier`, ומתי נבדקה לאחרונה (הישנות ראשונות).
2. להיכנס לאתר המעקב של הספקית ולקרוא את הסטטוס האמיתי.
3. `shipment_update` עם `status`, ו-`deliveredAt` **רק** כשהספקית אומרת שנמסר ונוקבת בתאריך.
   `sourceUrl` = הדף שנקרא.

**ב. שטרי מטען חדשים בתיבת המייל** — כמו קודם: `bol_worklist` → חיפוש לפי
`poNumber` ← `pn` ← `orderNumber` ← `supplier` → `bol_submit_matches`.

**מחיר קנייה:** אם המייל או ההזמנה נוקבים במחיר קנייה ליחידה — נשלח כ-`buyPriceUsd`,
**בדולרים ובלי להמיר**. השרת מביא את השער היציג לתאריך המסירה וממיר בעצמו. המודל לא מחשב
שערים.

**האזהרה המרכזית שנכנסה לתיאורי הכלים:** שטר מטען הוא לא מסירה. `delivered` נשלח רק כשהסחורה
נמסרה בפועל — לא על "out for delivery" ולא על "arrived at facility".

## חשבוניות בלדר — למה יש אישור ומה קורה בו

חשבונית ספק רק **נרשמת**. חשבונית בלדר צריכה **לנחות** במקום מסוים: הכסף שלה הוא
`shipping_cost` של השורות שנשלחו, וזה מה שהסיכום החודשי מחסיר כדי להגיע לרווח. לכן זה המסך
היחיד שבו יש שלב אישור: עד שמישהו לא אמר לאילו שורות החשבונית שייכת, אין שורה ב-`courier_invoices`
בכלל — החשבונית יושבת ב-`staged_courier_invoices`.

**המפתח שהיה אמור לחבר את שני המסמכים הוא מספר שטר המטען:** הבלדר מדפיס אותו בחשבונית, ו-agent
המעקב אמור לכתוב אותו על השורה (`order_lines.bol`). בפועל הוא מלא בעשירית מהשורות, ולכן
השיוך נשען על ארבעה מפתחות ולא על אחד. בהעלאה:

1. החילוץ (Anthropic API — `src/lib/extract-courier-invoice.ts`) מחזיר את כותרת החשבונית
   ו**שורה לכל משלוח**: מספר מעקב, אסמכתא, מספר רשימון, פרטי השולח, תאריך, תיאור וסכום.
2. הקוד (`src/lib/courier-match.ts`) משייך כל משלוח לשורה, לפי ארבעה מפתחות בסדר הזה:

   | # | מפתח | מול | ודאות |
   |---|---|---|---|
   | 1 | מספר מעקב (מנורמל: אותיות וספרות, בלי רישיות) | `order_lines.bol` | ודאי |
   | 2 | האסמכתא שהבלדר מצטט | `order_lines.po_number` | ודאי |
   | 3 | אותה אסמכתא | `orders.order_number` | ודאי |
   | 4 | ספק + חלון תאריכים | `order_lines.supplier` + `orders.order_date` | **משוער** |

   מפתחות 1–3 מזהים משלוח. מפתח 4 **מסיק** אותו, ולכן הוא אחרון ומוסגר (ראו למטה).
   משלוח אחד שמכסה כמה שורות מתפצל ביניהן, והאגורות העודפות נופלות על השורה הראשונה כדי
   שהסכום יסתכם בדיוק — אבל **מפתח הספק לעולם לא מפצל**: פיצול הוא טענה שמשלוח אחד כיסה
   כמה שורות, ומספר מעקב מבסס אותה, צירוף מקרים של ספק ותאריך לא. משלוח שלא זוהה נשאר לא
   משויך.
3. הכרטיס הממתין מציג את הכל לעריכה (כולל קישור למסמך המקורי) ורק "אישור" כותב למסד:
   החשבונית, הקובץ, שורות השיוך ועלות המשלוח על השורות — הכל בטרנזקציה אחת.

### מפתח הספק: משוער, מוסגר, ולא הופך לכסף לבד

`order_lines.bol` מלא בפועל בעשירית מהשורות, ולכן חשבונית שמצטטת רק שט"מ — למשל חשבונית מיסי
יבוא של DHL, שנותנת שט"מ, מספר רשימון, פרטי שולח ותאריך יבוא ו**שום אסמכתא שלנו** — לא נתפסה
באף מפתח והשאירה את כל הטבלה למילוי ידני. מפתח הספק סוגר את הפער: אותו ספק (לפי
`suppliersMatch` — נרמול והכלת טוקנים, לא דמיון מטושטש), הזמנה בתוך חלון של
`SUPPLIER_WINDOW_DAYS` יום לפני המשלוח, וחיתוך עם שורות **פתוחות שאין להן עלות משלוח רשומה**.
**שתי מועמדות = לא בוחרים** — שתיים זו שאלה פתוחה, לא התאמה של 50%.

מה שהוא מציע מסומן `matchedBy: "supplier"`, והתג נשמר ב-payload. משם:

- הטבלה מציגה את השורה בגוון נפרד, עם הסבר שזה שיוך משוער וכפתור **"מאשר את השיוך"**.
- `allocationsFromShipments` **מדלגת** על שיוך משוער — הוא לא הופך לעלות, לא משנה מי קורא לה.
- `approveCourierInvoice` **חוסמת** אישור כל עוד יש שיוך משוער שלא אושר.

אישור (או בחירת שורה אחרת) מסב את התג ל-`"manual"`, ורק אז העלות נרשמת. **שיוך משוער לא נרשם
בשקט כאילו הוא מספר מעקב.**

### מספר רשימון לא נכנס לאסמכתא

בחשבונית מיסי יבוא אין אסמכתא שלנו, והמודל נטה למלא את שדה האסמכתא במספר הרשימון — מספר
שמובטח לא להתאים, ושאם יתנגש עם מספר הזמנה קיים ישייך את החיוב לשורה הלא נכונה. הרשימון קיבל
שדה משלו (`customsDeclaration`), הפרומפט אומר במפורש שאסמכתא ריקה היא התוצאה הנכונה כשאין
אסמכתא, ואם המודל מחזיר בכל זאת אסמכתא שזהה לרשימון — הנרמול מוחק אותה ומוסיף warning.

כללים שנשמרים אחרי האישור:

- `order_lines.shipping_cost` הוא **תמיד** סכום השיוכים של השורה. לכן עריכת שיוך או מחיקת
  חשבונית מחשבת את הערך מחדש — ושורה שאיבדה את השיוך שלה חוזרת לריק, ולא נשארת עם מספר
  שאין לו מסמך.
- שתי שורות שיוך לאותה שורת הזמנה מתמזגות לשיוך אחד (הסכום מסתכם), כך שהחישוב חד-משמעי.
- חשבונית במטבע זר לא ניתנת לשיוך: אין המרה מומצאת. יש להזין את הסכום בשקלים.
- גם הזנה ידנית עוברת דרך אותה המתנה לאישור, כדי שיהיה דלת אחת אל הספר.

## חילוץ PDF — מודל, קאשינג ועלות

שלושת המחלצים (`extract-order`, `extract-invoice`, `extract-courier-invoice`) קוראים ל-Anthropic
API באותה תבנית: `system` + הגדרת כלי אחת + ה-PDF, עם `tool_choice` כפוי כדי שהפלט יהיה מובנה.

- **המודל** הוא `EXTRACT_MODEL ?? "claude-sonnet-5"`.
- **`system` וההגדרת כלי זהים בכל העלאה**, ולכן שניהם מקושטים ב-`cache_control` על בלוק ה-system
  האחרון. סדר הרינדור הוא `tools` → `system` → `messages`, כך שנקודה אחת תופסת את שניהם, וקריאה
  מקאש היא כעשירית ממחיר הקלט. ה-PDF יושב ב-`messages` — אחרי הנקודה — ולכן הבייטים שלו לא
  נכנסים לקידומת המקושטת, וזה מה שמאפשר לקידומת להיות זהה בין מסמכים שונים.
- **שתי מלכודות שכדאי להכיר לפני שינוי:**
  1. הקידומת חייבת לעבור את המינימום של המודל, אחרת **אין קאשינג ואין שגיאה** (רק
     `cache_creation_input_tokens: 0`). ב-`claude-sonnet-5` המינימום הוא 1024 טוקנים ושלושת
     הפרומפטים עוברים אותו. דריסת `EXTRACT_MODEL` למודל עם רצפה גבוהה יותר (Opus 4.6 ו-Haiku 4.5
     דורשים 4096) מכבה את הקאשינג בשקט.
  2. כתיבה לקאש עולה כ-1.25×, קריאה כ-0.1×, וה-entry חי 5 דקות. **שתי העלאות בתוך החלון מחזירות
     את הכתיבה; חשבונית אחת ביום משלמת את הפרמיה ולא קוראת כלום.** זה רווח כשחשבוניות מגיעות
     באצווה, והפסד קטן כשמעלים אחת בודדת.
- **`effort: "medium"`** במקום ברירת המחדל `high`: קריאת טבלה מ-PDF אינה משימת הסקה (וממילא
  `thinking` כאן `disabled`, מה שמצמצם את השפעת ה-effort מלכתחילה).
- **`max_tokens` הוא תקרה ולא יעד** — קיצוץ שלו לא חוסך טוקנים, רק מסכן קטיעה של הפלט
  (`stop_reason: "max_tokens"` מפיל את כל החילוץ). ה-PDF עצמו הוא רוב הטוקנים ואין שם מה לחסוך.

## חוקי הסטטוס (מסך הזמנות פתוחות)

לפי סדר עדיפויות:
1. סטטוס ידני: הגיע=ירוק, סופק חלקי=כתום, מאחר=אדום (גובר על הכל)
2. **הספקית אישרה מסירה (`shipment_status = 'delivered'`) → ירוק**
3. הספקית מדווחת תקלה (`exception`: מכס, עיכוב, סירוב) → כתום
4. תאריך אספקה חוזי עבר → אדום
5. שטר מטען מלא → **כחול ("במשלוח")**
6. "סופק" (בלי "לא סופק") בעדכון אספקה/הערות → כתום
7. אחרת → ניטרלי

**ירוק אומר שהסחורה הגיעה, ורק הספקית יכולה לומר את זה.** שטר מטען הוא מסמך שאומר שקרטון
יצא ממחסן; עד לתיקון הזה הוא צבע שורה בירוק, וזה היה הבאג: משלוח שיושב במטוס נראה בדיוק כמו
משלוח שנמסר וחתום. מעכשיו שטר מטען קונה **כחול**, וירוק מחכה לסטטוס מסירה מ-FedEx / DHL /
UPS. זה נכון גם כשהמספר נכתב אוטומטית ע"י agent המעקב, וגם כשיש "סופק" בהערות.

**מסירה גוברת על האיחור.** זה היפוך מכוון של כלל קודם שהשאיר שורה מאוחרת אדומה לנצח: ברגע
שהסחורה פיזית כאן, שורה אדומה משקרת יותר מירוקה. האיחור לא נמחק — השורה מקבלת תג
**"נמסר באיחור"**, והצבע מדווח איפה הסחורה נמצאת ולא איך התנהל החוזה. שורה שיש לה רק שטר
מטען ועברה את התאריך **נשארת אדומה**: משלוח שבדרך הוא כחול במקרה הטוב, ואיחור נשאר איחור
עד שהמשלוח באמת נוחת.

**תקלה נבדקת לפני התאריך** כי משלוח שתקוע במכס הוא בעיה שאפשר עוד לטפל בה, ואדום ("מאחר")
מתאר תאריך שכבר עבר.

מה שגובר על הכל הוא **סטטוס ידני בלבד**: רק אדם יכול לומר שהשורה נסגרה ("הגיע" → ירוק,
"סופק חלקי" → כתום), וסימון ידני "מאחר" גובר גם על אישור מסירה של הספקית.

## שער הדולר היציג — המקום היחיד שבו ממירים מטבע

הזמנות הרכש לספקים נקובות **בדולרים**, והסיכום החודשי מסכם **בשקלים**. מאז השינוי הזה
ההמרה נעשית פעם אחת, בשרת, לפי **השער היציג של בנק ישראל בתאריך המסירה**, והשער נשמר על
השורה לצד המספר שהוא ייצר:

| טור | מה יש בו |
|---|---|
| `buy_price_usd` | המחיר כפי שהוא בהזמנת הרכש, בדולרים, בלי המרה |
| `buy_price` | אותו מחיר בשקלים — **זה מה שכל חשבון הרווח מסכם, כמו קודם** |
| `fx_rate` | השער שבו הומר |
| `fx_rate_date` | היום שבו השער הזה פורסם |
| `fx_rate_source` | `boi` (אוטומטי) או `manual` (אדם הזין ביד) |

**למה השער נשמר ולא מחושב בזמן תצוגה:** דוח שנפתח פעמיים חייב להראות אותו רווח. המרה בזמן
רינדור הייתה משנה את הרווח של יוני בכל פעם שהדולר זז.

**השער היציג מתפרסם פעם ביום עסקים** ולא מתפרסם בשבת, בשישי ובחגים — ולכן החיפוש הוא "השער
האחרון שפורסם עד התאריך" ולא "השער של התאריך". משלוח שנמסר בשבת מומר בשער של חמישי, ו-
`fx_rate_date` אומר שזה היה חמישי. **שער שלא נמצא נשאר `NULL`**, הרווח מוצג "ממתין", ואף
פעם לא מנוחש — מספר שגוי מתחזה לרווח, ומספר חסר לא.

מקורות (שניהם ציבוריים, בלי מפתח, ושניהם נבדקו מול תשובה אמיתית ב-23/08/2026):

```
# סדרה היסטורית — זה מה שמשמש להמרה
https://edge.boi.gov.il/FusionEdgeServer/sdmx/v2/data/dataflow/BOI.STATISTICS/EXR/1.0/RER_USD_ILS?format=csv&startPeriod=…&endPeriod=…

# שער נוכחי בלבד — fallback
https://www.boi.org.il/PublicApi/GetExchangeRate?key=USD
```

שלוש עובדות שנמדדו ולא נוחשו, וכל אחת מהן הייתה יכולה לשבור את ההמרה בשקט:

1. **ה-CSV מגיע עם שתים-עשרה עמודות מפתח לפני התצפית** (`SERIES_CODE,FREQ,BASE_CURRENCY,…,UNIT_MULT,COMMENTS,TIME_PERIOD,OBS_VALUE,RELEASE_STATUS`).
   לכן הפרסר קורא `TIME_PERIOD` ו-`OBS_VALUE` **לפי שם בכותרת ולא לפי מקום**.
2. **`UNIT_MULT` (בסדרה) ו-`unit` (ב-PublicApi) הם חזקה של עשר ומספר יחידות:** היֶן מצוטט
   1.8873 ש"ח, וזה המחיר של **100** יֶן (`UNIT_MULT=2`, `unit=100`). שני הפרסרים מחלקים בזה.
   הדולר והאירו שניהם ביחידה אחת — וזה בדיוק למה אפשר לפספס את זה.
3. **`lastUpdate` הוא יום הפרסום האחרון ולא היום.** קריאה ב-23/08 (יום ראשון) מחזירה את
   השער של 21/08, וזו התשובה הנכונה.

שני ה-hosts (`edge.boi.gov.il` ו-`edge.boi.org.il`, וכן `www.boi.org.il` ו-`boi.org.il`)
עונים זהה, ושמות טווח התאריכים עובדים גם `startPeriod` וגם `startperiod`. נבחרו הצורות
שבנק ישראל מקשר אליהן בתיעוד שלו.

> **בפיתוח מקומי מאחורי proxy:** ה-`fetch` המובנה של Node מתעלם מ-`HTTPS_PROXY`. אם ההמרה
> מחזירה `NULL` מקומית בלי סיבה, זה זה — להריץ עם `NODE_USE_ENV_PROXY=1`. בפרודקשן (Vercel)
> אין proxy והבעיה לא קיימת.

השערים נשמרים בטבלת `fx_rates` (שורה ליום פרסום), כך שחודש של מסירות עולה קריאות בודדות.
כתיבה לקאש היא `on conflict do nothing` בכוונה: שער של יום שכבר ידוע לא משתנה מתחתנו, כי
שורות כבר הומרו לפיו.

**מה עדיין לא מומר:** שיוך עלות משלוח מחשבונית בלדר שאינה בשקלים נשאר **חסום**. ההחלטה על
הזמנות רכש לא מרפה את החסימה הזאת.

עריכה ידנית של `buy_price` במסך העריכה מעבירה אליו בעלות (`fx_rate_source` הופך ל-`manual`),
ומאותו רגע הריצה האוטומטית לא נוגעת בו — בדיוק כמו הכלל שקיים על `bol`.

**המרה חוזרת להיסטוריה:** `npm run fx:backfill` (דוח בלבד) / `npm run fx:backfill -- --apply`.

## אבטחת הכניסה

הסיסמה המשותפת היא השער היחיד למערכת, ולכן `/login` מוגן מפני ניחוש: **8 ניסיונות כושלים
מאותה כתובת IP בחלון של 15 דקות** נועלים אותה, וההודעה למשתמש מציינת כמה זמן נשאר. החלון
מחליק — הנעילה משתחררת מעצמה כשהכשלון הישן יוצא מהחלון, בלי צורך בהתערבות. ניסיון כושל,
נעילה והצלחה נרשמים ב-`audit_log` (**הסיסמה שנוסתה לא נרשמת אף פעם**).

הניסיונות נשמרים בטבלת `login_attempts` ולא בזיכרון התהליך, כי ב-Vercel יש כמה instances
ו-cold starts היו מאפסים מונה מקומי. השורות נמחקות בכניסה מוצלחת ומתיישנות מחוץ לחלון.

הכללים עצמם מבודדים ב-`src/lib/login-throttle.ts` (טהור, עם בדיקות יחידה) בנפרד מהגישה
ל-DB ב-`src/lib/login-attempts.ts`.

## מבנה עתידי

האימות (סיסמה משותפת) מבודד ב-`src/lib/auth.ts` + `src/proxy.ts` — מוכן להחלפה ב-auth רב-משתמשים בעתיד בלי לגעת בשאר הקוד. אימות הטוקנים של ה-API מרוכז ב-`src/lib/api-auth.ts`.

כל מוטציה נרשמת ב-`audit_log`, כולל `actor` — `user` לכתיבה אנושית, `agent:bol-tracking` /
`agent:ingest` לכתיבות אוטומטיות, `anon` לאירועי כניסה. כשיתווסף auth רב-משתמשים, זו העמודה
שתקבל את זהות המשתמש.
